From Coding Agents to Engineering Systems

A vendor-agnostic architecture for planning, implementation, verification, independent challenge, persistent memory, and evaluation in autonomous software engineering systems.

Planner decides. Worker implements. Verifier proves. Challenger attacks. Memory remembers.

01 — Framing

Roles should survive the tools that implement them.

Agentic coding systems are often described as a stack of product names: one model plans, another coding tool edits, a memory server stores context, and an orchestration runtime connects them. That is useful for setup, but weak as an architecture.

Models and tools will change. The more durable questions are about authority: who owns intent, who may mutate code, who verifies the result, who challenges assumptions, what belongs in persistent memory, and what evidence is required before the system may declare work complete.

If replacing a model or coding agent forces a redesign of the whole system, the architecture is coupled to products rather than capabilities.

The system described here was inspired by recent work on long-running coding agents, including Cursor's experiments with planners, workers, self-coordination, continuous executors, and recursive planning. Their results reinforced a useful idea: autonomy benefits from explicit ownership and bounded roles, while flat coordination and overloaded agents create pathological behavior.[1]

I treated that as a starting hypothesis and built a smaller local harness to test the same family of principles under observable, reproducible conditions.

02 — Durable principles

The products are adapters. These are the contracts.

01
Intent has one owner
Delegation distributes work, not accountability. One root role owns the user's objective until acceptance.
02
Planning and implementation are separate
A planner that also edits everything tends to collapse into a worker.
03
Workers are bounded
Each worker receives a narrow objective, scope, constraints, and completion condition.
04
Verification is authoritative
Worker self-report is evidence, not proof. Acceptance belongs to an independent verification step.
05
Challenge is different from implementation
An independent challenger should be free to disagree with the implementation path rather than continue it.
06
Memory is knowledge, not coordination
Persistent memory stores decisions, conventions, discoveries, and lessons—not locks, task queues, or worker status.
07
Project identity must be explicit
Long-lived tool processes may run from the wrong directory. Route state from the authoritative workspace.
08
Parallelism requires isolation
Independent mutation-capable workers need isolated workspaces or worktrees before results are integrated.
09
Observability is part of correctness
A system should be able to reconstruct who acted, with which permissions, on which workspace, and with what result.
10
Policies should become invariants
Natural-language constraints are useful, but cardinality, mutability, and approval boundaries eventually need runtime enforcement.
11
Failure should degrade capability, not assurance silently
Quota exhaustion, provider failure, tool denial, and memory outages are normal operating conditions.
12
Completion requires evidence
“Done” should be a verified state transition, not a confidence statement from a child agent.
03 — Architecture

A small number of roles with clear authority.

Capability graph
flowchart TD
    H[Human / Goal Owner] --> R[Root Planner]
    R -->|complex scope| P[Subplanner]
    R -->|bounded task| W[Implementation Worker]
    P --> W
    R --> V[Authoritative Verifier]
    R -->|independent review| C[Challenger]
    R <--> M[(Durable Memory)]
    W --> G[(Repository)]
    V --> G

Root planner

Owns the user's intent, global decomposition, routing, integration decisions, final acceptance, and durable-memory lifecycle. It should understand enough of the repository to make good decisions, but routine implementation belongs elsewhere.

Subplanner

Owns one bounded domain. It decomposes that scope further when necessary and hands precise tasks to workers. Recursive planning is allowed, but the hierarchy should remain as shallow as the task permits.

Implementation worker

Owns one scoped code change. It may inspect, edit, and run local checks according to its permissions, then returns a concise handoff. It does not own final acceptance.

Verifier and challenger

Verification proves that acceptance criteria are satisfied. Challenge is a separate assurance function: an independent reasoning path looks for defects, missed requirements, or unnecessary changes. Model diversity can help here, but diversity is a tactic rather than the architectural principle.

Durable memory

Memory stores project knowledge that should survive sessions: architecture decisions, stable conventions, recurring problems, important discoveries, and reusable lessons. Runtime coordination remains outside memory.

Control loop
flowchart TD
    A[Understand] --> B[Plan]
    B --> C[Delegate]
    C --> D[Implement]
    D --> E[Verify]
    E -->|failed| F[Rework]
    F --> C
    E -->|passed| G[Challenge]
    G -->|defect| F
    G -->|accepted| H[Remember]
    H --> I[Complete]
04 — Reference implementation

One concrete stack, explicitly treated as temporary.

The first validated implementation was built on Windows in September 2026. Its purpose is to make the principles executable, not to define the architecture in terms of any one vendor.

05 — Validation

The first test was intentionally trivial.

The repository contained a small JavaScript function and one baseline test. The harness was asked to add safeDivide(a, b), throw on division by zero, add exactly three tests, introduce no dependencies, and make no unrelated changes.

The task itself was not the experiment. The orchestration path was.

06 — Findings

The imperfections were more useful than a clean demo.

01Prompt policy is not structural policy

The run requested exactly one implementation worker. The subplanner still created another worker for verification.

Implication: worker cardinality and role permissions should become runtime-enforced invariants.

02Worker verification was not authoritative

An unattended coding worker could edit files but hit an approval boundary when attempting to run the test command.

Implication: final acceptance should remain with a trusted verifier until worker execution policy is strong enough.

03One-shot children were not fully visible in one view

After completion, the continuable-agent list contained no one-shot children. Run records were needed to reconstruct participation.

Implication: lineage requires a durable trace plane, not only live-agent state.

04The memory process cwd was not the active project

Implicit project detection could resolve the harness repository instead of the current workspace.

Implication: session/project identity must be established explicitly from authoritative workspace context.

05Provider limits are part of normal operation

An earlier dry run reached the independent reviewer's quota while the rest of the hierarchy completed successfully.

Implication: the system needs graceful degradation and an explicit reduction in assurance when a role is unavailable.

06Memory metadata can disagree with session routing

Session routing and search resolved the correct repository while one direct observation lookup surfaced inconsistent project metadata.

Implication: project-identity assertions belong in memory integrity checks.

07 — Research roadmap

The goal is to earn stronger claims, not add more agents.

V0.2

Role conformance

Move mutability, reviewer immutability, worker limits, and authority boundaries from prompts into runtime policy.

V0.3

Multi-project memory isolation

Test several repositories, overlapping terms, renames, remotes, monorepos, and ambiguous project resolution.

V0.4

Failure recovery

Inject provider outages, quota exhaustion, timeouts, malformed child output, shell denial, test failure, and memory outages.

V0.5

Parallel isolated workers

Use Git worktrees or equivalent isolation and measure speedup, conflicts, duplicated work, integration errors, and token overhead.

V0.6

Routing policy

Measure when a default worker, stronger worker, or model-diverse challenger improves outcome enough to justify its cost.

V0.7

Single strong agent vs hierarchy

Run the same 20+ task corpus under both conditions and compare correctness, time, tokens, retries, defects, and human intervention.

V0.8

Long-horizon engineering

Test multi-hour work, context compaction, interruptions, resume, evolving requirements, and intent drift.

V0.9

Completion correctness

Turn “done” into a machine-checkable acceptance state with negative tests and incomplete-implementation traps.

V0.10

Adversarial security

Red-team repository prompt injection, memory poisoning, secret exfiltration, malicious MCP output, destructive commands, and supply-chain attacks.

V1.0+

Autonomous security engineering

Apply the same role contracts to vulnerability validation, detection engineering, DFIR, BAS, and incident-response automation.

Metrics that should become first-class

  • task success
  • acceptance criteria satisfied
  • tests passed
  • defects found after completion
  • unrelated file changes
  • delegation count
  • role violations
  • retry count
  • root interventions
  • human interventions
  • wall-clock time
  • token usage
  • provider cost
  • parallel speedup
  • merge conflicts
  • memory routing accuracy
  • memory retrieval precision
  • cross-project leakage
  • lineage completeness
  • rollback success
The experiment that matters most is simple: does hierarchical orchestration actually outperform one strong agent on a repeatable task corpus?

Until that A/B test exists, hierarchy is a plausible engineering architecture, not a performance claim.

08 — Current claim

What V0.1 proves, and what it does not.

V0.1 does not prove that hierarchy is cheaper, faster, or more correct than a single strong agent. It does not establish long-horizon reliability, adversarial robustness, or safe autonomous deployment.

It does establish a working control loop: planning can be separated from implementation; implementation can be independently verified; a model-diverse challenger can review the result; durable project memory can survive conversations; and failure modes can be observed precisely enough to become the next set of experiments.
