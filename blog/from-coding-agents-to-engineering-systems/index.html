From Coding Agents to Engineering Systems

Coding agents can read repositories, change code, run tools, and preserve state. I now treat them as privileged processes, with explicit authority boundaries and evidence requirements. This note describes the architecture I use, one small eval, and the parts that did not behave as designed.

Planner decides. Worker implements. Verifier proves. Challenger attacks. Memory remembers.

Coding agents are privileged processes.

A coding agent can read a repository, change files, run commands, call external tools, and preserve information after the conversation ends. I had been thinking about those capabilities as conveniences. Building this system pushed me toward a stricter model: the agent is a privileged process, and its authority should be explicit.

That model changes the design questions. Who owns the user's intent? Which role may mutate the repository? Who checks the result? Who can challenge an implementation? What may survive into another session? What evidence is required before completion? A stack of product names does not answer any of them.

I started from Cursor's published work on planners, workers, self-coordination, and recursive planning.[1] I could not inspect their internal system or reproduce its scale. I wanted a smaller system I could run on one machine, open up, and watch fail. That led to a capability architecture whose components are defined by authority rather than by vendor.

Replacing a model, coding tool, memory service, or orchestrator should replace an adapter. The authority contracts should survive.

This version shows that a role-based system can complete one small task while still violating one of its own role constraints. It contains no comparison with a single strong agent. That gap between the declared system and the executed system now drives the role-conformance work in V0.2.

This is a working engineering note. I use the system today and expect its adapters to change. Some principles may change too as later evaluations test the assumptions that V0.1 could not reach.

Twelve principles with different levels of evidence.

I wrote these principles as design constraints for the system. They did not all come from the eval. Several borrow familiar ideas from security and software engineering: one owner for intent, separation of duties, least privilege, explicit identity, and acceptance backed by evidence. The recorded runs reinforced some of them. Two remain largely untested hypotheses. Keeping those categories separate prevents a single successful test command from carrying claims it cannot support.

Constraints I brought into V0.1

These shaped the implementation before the validated run began. V0.1 exercised parts of them, but it was too small to establish that they are sufficient or optimally drawn.

01
Intent has one owner
One root role owns the user's objective through final acceptance. Delegation distributes work while accountability remains with the root.
02
Planning and implementation are separate
Decomposition and repository mutation carry different authority. A planner may inspect enough to decide without becoming the routine implementer.
06
Memory is knowledge, not coordination
Persistent memory holds decisions, conventions, discoveries, and reusable lessons. Locks, worker status, task queues, and temporary todos belong to runtime coordination.
12
Completion requires evidence
Completion is an acceptance state backed by relevant checks. A worker's confidence statement cannot create that state.

Constraints reinforced by the recorded behavior

The validated end-to-end run reinforced boundaries around workers, verification, project identity, policy, and lineage. The earlier dry run reinforced the need to report reduced assurance when a provider disappears. Each finding later in the note names its run.

03
Workers are bounded
A worker receives one objective, explicit scope, constraints, and acceptance criteria. It should not need global authority to finish local work.
04
Verification is authoritative
Worker self-report is evidence for a verifier to inspect. Final acceptance belongs to a role that can inspect the diff and run the required checks.
07
Project identity must be explicit
A long-lived tool process may have a different working directory from the active workspace. Memory and state must route from authoritative workspace context.
09
Observability is part of correctness
The record should identify which actor ran, with which authority, on which workspace, and with what result. Live process lists alone do not preserve that history.
10
Policies should become invariants
Prompts can express intent. Cardinality, write access, reviewer immutability, and approval gates need runtime enforcement when conformance matters.
11
Failure should reduce capability without hiding reduced assurance
Quota exhaustion, provider failure, tool denial, and memory outages should produce an explicit status that says which assurance step did not run.

Open hypotheses

V0.1 did not test parallel mutation in isolated workspaces. It also did not place a known defect in front of the challenger or compare different reviewer models. These principles describe the intended boundary and the next questions. The results have yet to be earned.

05
Challenge is different from implementation
A challenger needs authority to disagree with the implementation path and no authority to patch the work it is judging. Whether model or provider diversity improves that challenge remains unmeasured.
08
Parallelism requires isolation
Independent workers that can mutate code should receive isolated workspaces or worktrees, followed by an explicit integration step. V0.1 did not test this configuration.

I expect the authority and evidence principles to travel better than the current choices about model size, routing, or recursion depth. That expectation is still a design judgment. The roadmap includes the comparisons needed to test it.

Architecture: roles are authority boundaries.

Capability graph
flowchart TD
    H[Human / Goal Owner] --> R[Root Planner]
    R -->|complex scope| P[Subplanner]
    R -->|bounded task| W[Implementation Worker]
    P --> W
    R --> V[Authoritative Verifier]
    R -->|independent review| C[Challenger]
    R <--> M[(Durable Memory)]
    W --> G[(Repository)]
    V --> G

A box in this graph names an authority boundary. It does not require a separate agent, model, operating-system process, or machine. One runtime actor may hold more than one logical role if the acceptance and mutation boundaries remain visible. A deployment may also split one role across several actors.

V0.1 makes that distinction concrete. The root planner also performed authoritative verification with Git, PowerShell, and the project's tests. There was no separate verifier agent. I still model verification as its own role because the worker could not grant final acceptance, and the root had to switch from planning authority to an evidence-producing verification step.

Planner

The root planner owns intent, decomposition, routing, integration decisions, final acceptance, and the durable-memory lifecycle. A subplanner owns only the bounded domain delegated to it. It can decompose that domain and report upward, but it cannot accept the full objective or take over global memory. The subplanner is a narrower planner role and never becomes another root.

Worker

The worker owns one bounded implementation. It may inspect and modify the repository within its permissions and run local checks the environment allows. Its report should name the changes, checks, discoveries, and unresolved issues. That report informs acceptance; it cannot declare acceptance.

Verifier

The verifier owns acceptance evidence: diff inspection, tests, builds, linting, static analysis, and checks for unrelated changes as the task requires. Independence here means authority over the acceptance decision. V0.1 assigned that authority to the root rather than creating another runtime actor.

Challenger

The challenger follows a separate review path and looks for correctness defects, requirement gaps, edge cases, and unnecessary changes. It should report and stop. If the challenger edits the work under review, it becomes another implementer and needs a new review. My current adapter uses Codex to introduce model and provider diversity. That is a design choice. V0.1 did not measure whether diversity improves defect detection.

Memory

Memory preserves project knowledge that should outlive a conversation: decisions, conventions, non-obvious discoveries, and reusable lessons. Runtime scheduling, worker status, locks, and temporary todos remain in the coordination layer. The separation reduces the chance that stale progress is recalled later as current state.

Control loop
flowchart TD
    A[Understand] --> B[Plan]
    B --> C[Delegate]
    C --> D[Implement]
    D --> E[Verify]
    E -->|failed| F[Rework]
    F --> C
    E -->|passed| G[Challenge]
    G -->|defect| F
    G -->|accepted| H[Remember]
    H --> I[Complete]

The control loop also describes logical stages. A runtime may combine stages in one process, as V0.1 did for planning and verification. The trace still needs to show which authority was active and what evidence moved the task forward.

Reference implementation: the adapters I use today.

The architecture above can be implemented by many stacks. This is the one I run today. DSH supplies orchestration and scoped tools. Claude Opus 5 fills the root planner role, Claude Sonnet 5 the subplanner role, Claude Code the worker role, Codex the challenger role, and Engram the memory role. The root also fills the verifier role with Git, PowerShell, and project tests.

I made the model assignments as design decisions. I chose a larger reasoning budget for the root, a lower-cost planner for bounded decomposition, and a different provider for challenge. The records do not show that Opus repays its cost, that Sonnet is sufficient for harder decomposition, or that Codex fails differently enough to catch more defects. V0.6 is where those routing assumptions become experiments.

I expect these adapters to change. Replacing Claude Code with another repository worker should leave worker authority unchanged, and replacing Engram should leave the memory boundary unchanged. A separate verifier process could take over the evidence step without changing what verification owns.

Portable contract

roles:
  root_planner:
    owns: [intent, decomposition, routing, acceptance, durable_memory]
    mutates_code: false

  subplanner:
    owns: [bounded_domain, decomposition]
    mutates_code: false

  worker:
    owns: [bounded_implementation]
    final_acceptance: false

  verifier:
    owns: [acceptance_evidence]
    trusts_worker_claims: false

  challenger:
    owns: [independent_review]
    mutates_reviewed_work: false

  stores: [decisions, conventions, discoveries, reusable_lessons]
  never_stores: [locks, worker_status, transient_todos]

This contract describes ownership without prescribing a process layout. A deployment can use one actor for the root and verifier, as V0.1 did, or split them. It still needs a record of who produced the acceptance evidence.

Where authority lives today

The current implementation divides constraints between prompt text and runtime policy. The root prompt is where intent ownership, verification duty, and completion authority are assigned, and it is worth reading as a contract rather than as instructions: 

You own the user's original objective and maintain global understanding
of the project until the objective is complete.

Do not perform routine implementation yourself with write, edit or
PowerShell. Delegate implementation to a worker.

Never blindly trust a worker result.

Never declare the objective complete merely because one worker reports
success.

Completion is your responsibility.

Two of those lines carry most of the weight. "Never blindly trust a worker result" is what keeps a worker's self-report from becoming acceptance, and "completion is your responsibility" is what stops the hierarchy from ending on a child's optimism. Neither is enforced by the runtime. Both are requests, which is the same weakness finding 01 exposes.

Memory receives an explicit allowlist of durable information and a denylist of coordination state: 

Good candidates include:
- architecture decisions
- important configuration decisions
- stable project conventions
- non-obvious discoveries
- completed bug fixes with reusable lessons
- recurring failure modes
- significant technical constraints
- patterns that future sessions should follow

Do NOT save:
- task progress
- worker status
- temporary hypotheses
- logs
- transient command output
- implementation chatter
- short-lived todo items
- agent coordination state

The subplanner receives narrower authority. It can inspect, decompose, and delegate, while durable memory and challenger access remain with the root: 

You are a SUBPLANNER in a hierarchical autonomous software
engineering system.

You own only the bounded objective delegated to you by your parent.

Do not directly implement code.

You do not have authority over durable project memory.

Do not start Engram sessions.

Do not save Engram memories.

Do not use Engram as a task queue, scratchpad, status mechanism,
lock manager or coordination channel.

You do not have access to Codex by policy.

Escalation to Codex belongs to the root planner.

Prefer the shallowest hierarchy capable of solving the problem.

These prompt rules express the contract, but the runtime cannot enforce every sentence. The subplanner's denied tools are structural policy: 

maxDepth: 2

toolFilter:
  deny:
    - write
    - edit
    - pwsh
    - subagent_codex

The preset removed four tools from the subplanner while leaving worker cardinality in prompt text. The subplanner could not call write, edit, pwsh, or subagent_codex. It could call the worker twice, because cardinality remained prompt text. V0.2 moves that boundary into runtime policy.

The complete preset and setup notes live in the implementation repository. These excerpts show the authority-bearing lines; the repository remains the source for reproduction.

V0.1: the safeDivide experiment.

The eval asked the system to add safeDivide(a, b) to a small JavaScript repository. Normal division had to return a / b. A zero divisor had to throw Error("division by zero"). The change required exactly three tests, no dependencies, and no unrelated edits.

The task was deliberately small. Removing application complexity as a major variable makes failures in orchestration, permissions, adapters, providers, and role boundaries easier to see. It does not remove every variable, isolate model behavior, or establish that this role design is better than a single agent.

The eval specified a route as well as an output. The root would delegate to one subplanner, which would use one implementation worker. The result would return to the root for authoritative verification, independent challenge, and a durable memory write.

Six findings across three runs.

Findings 01 through 04 come from the validated end-to-end run in result.md. Finding 05 comes from an earlier dry run. Finding 06 comes from the cross-session run in memory-result.md. I am keeping the run boundaries visible because each record supports a different claim.

01Validated run: prompt policy did not enforce worker cardinality

The eval required exactly one implementation worker. The subplanner made a second coding-agent call for verification. The implementation itself came from one worker, so functional correctness was unaffected. Role conformance still failed. The instruction was present; the runtime had no worker-count invariant.

Implication: enforce worker limits and concurrency rules in runtime policy when the route is part of the acceptance contract.

02Validated run: worker verification was not authoritative

The unattended worker encountered an approval gate when it tried to run npm test. It could not request the approval and therefore could not produce authoritative test evidence. The root ran the command and accepted the result. This preserved final verification, while exposing a capability gap in the worker path.

Implication: assign acceptance to a verifier that can run the required checks, and record when a worker's checks were blocked or incomplete.

03Validated run: one-shot children disappeared from the continuable view

Completed one-shot children did not remain in the continuable-agent list. The run records preserved evidence that they had executed, but the live view alone could not reconstruct the path after they exited.

Implication: preserve durable lineage separately from live process state.

04Validated run: implicit memory identity could select the wrong repository

The memory process working directory was not authoritative for the active project. Implicit detection could resolve the DSH repository. Explicit session initialization with the active workspace directory correctly resolved dsh-mini-demo. The record shows a routing risk; it does not record a cross-project memory write.

Implication: establish session and project identity from the active workspace before reading or writing persistent state.

05Earlier dry run: the challenger reached its provider quota

This happened in an earlier dry run, separate from the validated run. The independent reviewer reached its quota while the rest of the hierarchy completed successfully. The available evidence does not record how the quota event appeared in the final status or whether the system explicitly marked assurance as reduced.

The validated run had a different outcome: the challenger executed, reported no correctness defect, requirement violation, or unnecessary change, and received PASS. The dry-run quota event cannot be used to reinterpret that result.

Implication: provider loss should produce an explicit assurance status that names the missing step and prevents a reduced review path from looking complete.

06Cross-session run: memory metadata disagreed with session routing

Session initialization and search resolved dsh-mini-demo. A direct lookup of the retrieved observation surfaced a header naming the DSH repository, while the observation body concerned dsh-mini-demo. The stored convention was recalled correctly, so the record classifies this as a project-resolution or metadata inconsistency rather than a memory-content failure.

Implication: verify project identity on direct retrieval as well as at session start, and test for disagreement between routing and observation metadata.

What you can use without my stack.

The authority model carries over without these adapters. You can apply it with one agent, several agents, a homegrown supervisor, or a commercial orchestrator.

Keep final acceptance away from the implementation report. The same runtime actor may implement and run local checks, but completion should depend on evidence inspected by an authority that can reject the work. In V0.1, the worker could not run the final test command and the root performed verification.

Separate durable knowledge from runtime coordination. Define what may persist. Decisions, conventions, discoveries, and reusable lessons have a different lifetime from locks, worker status, logs, and temporary todos. Keeping both in one memory surface makes stale coordination easier to mistake for current state.

Make project identity an input. Pass the active workspace explicitly to any long-lived memory or tool process. Check the identity returned by the service before a read or write. Finding 06 adds a second check: compare retrieval metadata with the session identity.

Move critical constraints into policy. Prompts are useful for role descriptions and reporting formats. Use permission filters, approval gates, cardinality limits, isolated workspaces, and state transitions for constraints whose violation changes the result. The preset denied write tools structurally; its prompt-only worker limit was violated.

Record the executed path. Keep actor identity, assigned role, parent, workspace, permissions, tool results, and acceptance evidence long enough to reconstruct the run. A live agent list cannot provide that after one-shot processes exit.

Report assurance loss directly. If verification, challenge, memory, or a provider is unavailable, name the missing step in the final status. The earlier dry run establishes that quota loss can occur while the remaining hierarchy completes. Its record does not say whether the final status reflected that loss. A future status record should.

When this is overkill.

A small, local, reversible change with good test coverage probably does not need a hierarchy. One coding tool plus human diff review may be the clearer design. I use the simpler path when the work is easy to inspect and a mistake is easy to undo.

Explicit roles become more useful as authority and recovery get harder to reason about: long-running work, multiple repositories, several workers, different permissions or capabilities, sensitive changes, irreversible actions, audit requirements, cross-session memory, and security or production exposure. Even then, each additional runtime actor has to justify its coordination cost.

A logical verifier or challenger does not force another process. Start with the authority boundary. Split it into a separate actor only when independence, permissions, workload, or auditability requires that separation.

What these runs do not establish.

The validated evidence covers one small task and one execution path. It does not show that the hierarchy is more correct, faster, cheaper, or easier to operate than one strong agent. No single-agent baseline has been run. The record also lacks token counts, model-call counts, estimated cost, retries, wall-clock time, and human intervention data.

The task did not test long-running work, parallel isolated workers, adversarial input, production access, rollback, or destructive operations. The challenger found no defect, but the eval did not seed a known defect, so the result says nothing about detection rate. The memory follow-up shows successful recall and one metadata inconsistency; it does not establish isolation across many projects.

Finding 05 belongs to an earlier dry run, and finding 06 belongs to the cross-session memory run. Combining them with the validated run would create a broader story than any one execution supports.

I am willing to remove roles or abandon the hierarchy if the comparisons do not justify it. If one strong agent wins broadly on correctness, time, cost, and required human attention, the extra runtime actors are overhead. The authority boundaries may still be useful inside a simpler process, but this implementation would need to shrink.

Research roadmap.

The next versions turn current assumptions into comparisons, failure injection, and machine-enforced policy. I do not want to answer every problem by adding another agent. A new runtime actor should appear only when an experiment shows that a separate authority needs a separate process.

V0.2

Role conformance

Enforce planner mutability, worker acceptance limits, challenger immutability, memory boundaries, and worker cardinality in runtime policy.

V0.3

Multi-project memory isolation

Test several repositories, identical topic names, cross-session recall, renames, remotes, monorepos, and explicit ambiguity handling.

V0.4

Failure recovery

Inject unavailable workers, challenger quota exhaustion, timeouts, malformed child responses, test failure, shell denial, MCP outage, and memory-write failure. Measure detection, retry, fallback, rollback, and human escalation.

V0.5

Parallel isolated workers

Use worktrees or equivalent isolation and compare wall-clock time, conflicts, duplicated work, merge defects, and token overhead with serial execution.

V0.6

Routing policy

Compare same-model workers, stronger workers, a model-diverse challenger, and no challenger. Measure success, latency, tokens or cost, defect detection, and escalation. This is where the current model choices get tested.

V0.7

Single strong agent vs hierarchy

This baseline is pending. Run the same task, then a fixed corpus targeting 20 or more tasks, through one strong agent and through the hierarchy. Compare correctness, acceptance criteria, wall-clock time, model calls, tokens, estimated cost, retries, human interventions, unrelated changes, defects, and role violations where applicable.

V0.8

Long-horizon engineering

Test multi-hour work, many steps, context compaction, interruption and resume, changing requirements, and durable-memory recovery.

V0.9

Completion correctness

Define an explicit acceptance contract and test it with negative cases, incomplete implementations, and hallucinated test reports.

V0.10

Adversarial security

Attack the system with repository prompt injection, fake instructions, malicious tool output, memory poisoning, secret-exfiltration requests, destructive-command bait, dependency typosquatting, and privilege escalation.

V1.0+

Engineering system and domain transfer

Combine portable role contracts, reproducible evals, enforced invariants, isolated work, reliable memory, auditable lineage, recovery, and security tests. Then test which boundaries survive in vulnerability validation, detection engineering, DFIR, and incident response.

Metrics belong to the acceptance record

A task can be functionally correct while violating its route, omitting a review step, or changing unrelated files. Future reports should keep output correctness, role conformance, assurance status, resource use, and human intervention separate. V0.1 records enough to expose the worker-count failure, but not enough to compare efficiency.

The pending comparison asks whether the hierarchy earns its extra machinery on a defined class of tasks.

What V0.1 demonstrated.

In the validated run, the root delegated through a subplanner, one worker produced the implementation, the root ran authoritative verification, the independent challenger reported, and memory routing and writing succeeded. The repository result met the functional requirements. The executed route also contained an unrequested second coding-agent call, so role conformance failed.

The separate memory run showed that a new conversation could recall the stored project convention without inspecting the repository, using the explicit workspace identity. It also exposed inconsistent project metadata on direct observation lookup. The earlier dry run contributes only the quota finding described in finding 05.

These records make the role boundaries executable and give the next evaluations specific failure cases. They do not rank this system against a single strong agent. The current preset, eval definition, and result files are in the implementation repository. The pending V0.7 comparison must supply correctness, time, calls, tokens, cost, retries, interventions, unrelated changes, defects, and conformance data before I can argue that the hierarchy earns its overhead.
