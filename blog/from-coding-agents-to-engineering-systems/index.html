Roles should survive the tools that implement them.

The public conversation about agentic software engineering settled into a stack of product names: one model plans, another coding tool edits, a memory server stores context, an orchestration runtime wires them together. That is fine for a demo and weak as an architecture, because every name in that stack is a product decision, and product decisions change on a vendor's release schedule, not yours.

Models and coding tools will keep changing. What does not move as fast is authority: who owns intent, who may mutate code, who verifies the result, who can challenge the implementation path, what belongs in memory, and what evidence has to exist before anything calls itself done. Those are the same questions worth asking about any service account or process running with elevated privileges. An automated process with write access to a repository is, functionally, a privileged process, and one nobody can name the owner of is a finding, not a feature. I wanted coding agents held to that bar before trusting one near production code.

If replacing a model or coding agent forces a redesign of the whole system, the architecture is coupled to products rather than capabilities.

The starting point for this project was Cursor's public writing on long-running coding agents: planners, workers, self-coordination, continuous executors, recursive planning.[1] I took one idea from it seriously: autonomy gets better with explicit ownership and bounded roles, and worse with flat coordination and agents that accumulate authority nobody assigned them. I did not take their implementation, scale, or "self-driving codebases" framing as settled; it is a vendor's blog post written to sell a product, directionally useful but not something I would trust without testing it myself. So I built a much smaller version to see which parts survive once the product names change.

The products are adapters. These are the contracts.

None of the twelve principles below started as theory. They came out of watching the first version of this system misbehave in small, specific ways, then asking what rule would have stopped it. A few of them are close to obvious once you state them out loud. A few I only believe as far as one validated run lets me, and I say so directly in section seven.

01
Intent has one owner
Delegation distributes work, not accountability. One root role answers for the objective from the first prompt to final acceptance.
02
Planning and implementation are separate
The planner that understands the code best is also the one most tempted to change it directly. Separating the roles keeps that temptation from becoming a habit.
03
Workers are bounded
Each worker receives a narrow objective, scope, constraints, and completion condition, so a failure can be traced to the exact boundary it crossed.
04
Verification is authoritative
Worker self-report is evidence, not proof. Acceptance belongs to an independent step that can outrank the worker's own claim.
05
Challenge is different from implementation
An independent challenger should be free to disagree with the implementation path rather than continue it, and should never be the one who fixes what it finds.
06
Memory is knowledge, not coordination
Persistent memory stores decisions, conventions, discoveries, and lessons, not locks, task queues, or worker status that goes stale the moment a session ends.
07
Project identity must be explicit
Long-lived tool processes keep the directory they were launched from. Route state from the authoritative workspace, not from wherever the process happened to start.
08
Parallelism requires isolation
Independent mutation-capable workers need isolated workspaces or worktrees before results are integrated, or they corrupt each other's changes silently.
09
Observability is part of correctness
A system that cannot reconstruct who acted, with which permissions, on which workspace, and with what result is not ready to be trusted with anything irreversible.
10
Policies should become invariants
Natural-language constraints are useful, but cardinality, mutability, and approval boundaries eventually need runtime enforcement, because an instruction is not the same thing as a limit.
11
Failure should degrade capability, not silently reduce assurance
Quota exhaustion, provider failure, tool denial, and memory outages are normal operating conditions. The system should say so instead of finishing quietly as if nothing changed.
12
Completion requires evidence
"Done" should be a verified state transition, not a confidence statement from a child agent that has every incentive to report success.

The ones I would bet on surviving harder problems are tied to authority and evidence: one owner for intent, a worker's claim that is not proof by itself, memory that never carries runtime state. I am least sure about the ones that are a matter of degree: how bounded a worker should be, how deep recursive planning should go, how much model diversity buys a challenger. Those only held up in a single trivial run.

Root planner

Owns the user's intent, decomposition, routing, integration decisions, final acceptance, and the durable-memory lifecycle. It needs to understand enough of the repository to decide well, which is also the failure mode: a planner that reads enough code to plan well starts wanting to fix what it sees. I watched that happen in early sessions, small drive-by edits justified as "while I'm here." The boundary only holds if the planner's tools make implementation inconvenient. A prompt telling it not to bother is not enough on its own.

Subplanner

Owns one bounded domain, decomposes it further when necessary, and hands precise tasks to workers. Recursive planning is allowed, and in the validated run it used that latitude on its own initiative, which finding 01 covers in detail. The hierarchy should stay as shallow as the task allows: every extra layer is a place where an instruction can get reinterpreted instead of relayed.

Implementation worker

Owns one scoped code change. It may inspect, edit, and run local checks within its permissions, then hands back a concise report. It does not own final acceptance, and in this run it could not always run the checks it might claim responsibility for: it hit an approval boundary trying to execute the test command and had to hand that step back up rather than confirm it directly. That is the boundary working as intended. A worker that could always self-certify would make the verifier decorative.

Verifier and challenger

Verification proves that acceptance criteria are satisfied. It is not a vote or a summary. Challenge is a separate assurance function: an independent reasoning path looks for defects, missed requirements, or changes nobody asked for. Model diversity helps, but it is a tactic, not the reason the role exists. The harder discipline is making sure the challenger never fixes what it finds. A reviewer that quietly patches the code it is grading has stopped being independent, even when the patch is correct.

Durable memory

Memory stores project knowledge meant to outlive the conversation: architecture decisions, stable conventions, recurring problems, discoveries worth not rediscovering. What it does not hold is coordination state, for the reason principle 06 gives. A memory system that is sometimes right about live state is worse than one that makes no claim about it at all.

One concrete stack, explicitly treated as temporary.

The first validated implementation was built on Windows in September 2026, to make the principles executable, not to define the architecture around one vendor. Windows is also just the platform I work on. Most public writing about long-running coding agents assumes Linux or macOS, and running the same pattern from PowerShell surfaces path and process-identity assumptions that never show up in the demos.

Tested environment. Windows PowerShell, DSH 0.1.5-rc.1 and Engram 1.20.0. The configuration below is an implementation snapshot, not part of the vendor-neutral contract.

Each adapter earned its slot for a narrow reason, not because it is the best product in its category. DSH gives scoped tools, child agents, model routing, and traceable delegation in one runtime, the minimum a root planner needs to enforce the role contract instead of describing it. Opus plans because the root's job is mostly judgment under ambiguity, where the extra reasoning budget pays for itself. Sonnet runs the subplanner because a bounded domain does not need that budget. Claude Code implements because it is repository-aware and already bounded by design. Codex challenges for one reason above the rest: it fails differently than Claude does, the entire point of an independent reviewer. Engram holds memory because it is persistent, searchable, and project-scoped over MCP rather than baked into one vendor's session state. None of these are permanent. Any one gets replaced the day a better adapter meets the same requirement, and the role contract should not need to change.

    owns: [acceptance_evidence]

The memory adapter intentionally does not hard-code a project name, to prevent a specific failure. Engram runs as a long-lived MCP process started with engram mcp --tools=agent, and it keeps whatever directory it launched from, not necessarily wherever the root planner is coding right now. Hard-code --project and every repository you open can end up writing into the same bucket. The fix: the root reads its own working directory and passes it explicitly at mem_session_start, added after memory calls once came close to resolving against the wrong repository entirely.

The boundaries live in the prompts, until they don't.

Sections three and four describe the architecture. This section is the text each role actually receives, because prompts are where authority boundaries currently live. What follows is quoted from the preset that ran the validated session, trimmed to the lines that carry authority.

Root planner

The root persona opens with a claim about ownership before it says anything about tone or task: 

You are the ROOT PLANNER of a hierarchical autonomous software
engineering system, powered by {{model}}.

You own the user's original objective and maintain global understanding
of the project until the objective is complete.

Your primary responsibility is planning, decomposition, delegation,
integration reasoning, verification and durable project memory —
not routine implementation.

Do not perform routine implementation yourself with write, edit or
PowerShell. Delegate implementation to a worker.

Never blindly trust a worker result.

Never declare the objective complete merely because one worker reports
success.

Completion is your responsibility.

The "not routine implementation" line exists because I kept catching the root doing exactly that in early sessions. "Never blindly trust" exists because those same sessions took a worker's "done" at face value more often than I like admitting. Every line here is a scar, none of it written speculatively.

The memory rules get their own block because getting them wrong routes durable state into the wrong project without anyone noticing:

Never hard-code an Engram project name. Never infer the project from the MCP server process directory when the active workspace directory is available.

Section four covers why the process cannot be trusted to know this on its own; that gap cost me a session's worth of memory calls before this rule existed. The same persona then spells out a concrete save list: 

Good candidates include:
- architecture decisions
- important configuration decisions
- stable project conventions
- non-obvious discoveries
- completed bug fixes with reusable lessons
- recurring failure modes
- significant technical constraints
- patterns that future sessions should follow

Do NOT save:
- task progress
- worker status
- temporary hypotheses
- logs
- transient command output
- implementation chatter
- short-lived todo items
- agent coordination state

That second list is principle 06 as an instruction instead of a claim: everything on it is something an early version of this system tried to store as if Engram were a task queue.

Subplanner

The subplanner's persona is shorter, because it owns less: 

You are a SUBPLANNER in a hierarchical autonomous software
engineering system.

You own only the bounded objective delegated to you by your parent.

Do not directly implement code.

You do not have authority over durable project memory.

Do not start Engram sessions.

Do not save Engram memories.

Do not use Engram as a task queue, scratchpad, status mechanism,
lock manager or coordination channel.

You do not have access to Codex by policy.

Escalation to Codex belongs to the root planner.

Prefer the shallowest hierarchy capable of solving the problem.

Most of that list is things it is told not to do. Left unstated, memory writes or Codex access would have made it a second root planner with none of the accountability.

Where a prompt stops being enough

Everything above is a request, and the runtime does not know or care whether an agent reads its persona carefully. Worker cardinality is a request, which is what finding 01 in section seven exploited. The subplanner's tool access is not a request: 

maxDepth: 2

toolFilter:
  deny:
    - write
    - edit
    - pwsh
    - subagent_codex

A subplanner that calls write or pwsh gets no persona reminder; the tool is not there. That is principle 10 as configuration instead of prose. The pattern was not applied everywhere: worker cardinality stayed a sentence in the persona instead of a toolFilter entry, which is why finding 01 happened. A prompt is the wrong layer for anything you actually need to hold.

Implementation worker and challenger

Claude Code and Codex get configuration, not personas: provider: claude-code or provider: codex, both backgroundMode: one-shot, both maxDepth: provider-managed. What the root persona fixes instead is the shape every delegated task and worker report has to take:

Each delegated task must have one clear objective, explicit scope and boundaries, relevant technical constraints, expected verification, and a clear completion condition. Workers must return what they changed, tests or checks performed, important discoveries, unresolved issues, and recommended follow-up work.

one-shot mode is also why finding 03 happened: it runs, reports, and exits, and once it exits it stops showing up in DSH's live-agent list, which is exactly what I found looking for completed workers after the run.

None of this is enforced the way the subplanner's toolFilter is: the save and never-save lists are still prose, not policy. The complete preset, including every prompt quoted here, lives in the same agentic-engineering-harness repository, at presets/self-driving/agent.cordis.yml.

The first test was intentionally trivial.

The repository contained a small JavaScript function and one baseline test. The harness was asked to add safeDivide(a, b), throw on division by zero, add exactly three tests, introduce no dependencies, and make no unrelated changes.

A hard task would have made the result unreadable. If a genuinely difficult problem had failed, I would not have known whether the orchestration broke or the task was simply beyond what the models can do today, and those two failures look identical from the outside. A trivial task removes that ambiguity: if safeDivide does not get built correctly by five coordinating roles, the roles are the problem, full stop.

The task itself was not the experiment. The orchestration path was.

That is why the eval defines a required route, not just a required outcome: root to one subplanner, subplanner to one implementation worker, worker back to root, root to verification, root to an independent challenger, root to durable memory. Getting safeDivide right was necessary but not the point. The point was watching whether five roles with different authority stayed inside the boundaries I had drawn, or whether those boundaries were decorative the moment nobody read the prompt closely.

Cross-session memory

A completely new conversation, no repository inspection, no shell access, no delegation, initialized memory from the same workspace directory and recalled the exact convention written in the prior session: tests use Node's built-in node:assert/strict, npm test runs node test.js, and the project intentionally carries no dependencies or devDependencies. The root did not reconstruct any of that by reading files. It asked memory and got back the same answer a human would have found by reading the repository, without reading the repository.

The imperfections were more useful than a clean demo.

01Prompt policy is not structural policy

I had written the instruction plainly: exactly one implementation worker. I expected the subplanner to follow it, because it is a short, unambiguous sentence. It did not. It spawned a second worker to double-check the first one's diff, on its own initiative, because verifying its own delegation seemed reasonable in the moment. Nobody told it to skip that step, so it did not. The sentence was clear. The system had no mechanism that made ignoring it cost anything.

Implication: worker cardinality and role permissions should become runtime-enforced invariants, not instructions a subplanner is free to reinterpret.

02Worker verification was not authoritative

This is the one failure I actually wanted to see. If the worker had run npm test on its own and simply reported "tests pass," I would have had no way to tell a genuine pass from an optimistic one. Instead the approval policy blocked the shell call outright, forcing the worker to hand the claim back unverified and the root to run the tests itself. The failure I worried about, a worker misreporting a result in good faith, never got the chance to happen, because the environment would not let it self-certify.

Implication: final acceptance should remain with a trusted verifier until worker execution policy is strong enough to make a worker's own test run trustworthy.

03One-shot children were not fully visible in one view

When the run finished I went looking for the child agents to confirm what each had done, and the live-agent view had already forgotten about them. One-shot children do not persist in that list once they exit; only the run records kept the trail. Absence from the live view is not evidence of absence, but you cannot tell the difference from inside a tool that is supposed to show you.

Implication: lineage requires a durable trace plane, not only live-agent state.

04The memory process cwd was not the active project

I expected the memory server to just know which project it was talking to, the way most tools infer things from wherever you launched them. It cannot, safely, for the reason sections four and five cover. Left to implicit detection, this session would have written durable memory against deepseek-harness, the tool's own repository, while I worked in a different project entirely. Not a hypothetical, the default behavior.

Implication: session/project identity must be established explicitly from authoritative workspace context.

05Provider limits are part of normal operation

The rest of the hierarchy did not notice or care. Root, subplanner, and worker all finished as if nothing were wrong; the only signal that assurance had dropped was that the challenger's step never produced output. That is the failure mode that matters: not the loud crash, the silent skip reported upstream as a clean run.

Implication: the system needs graceful degradation and an explicit reduction in assurance when a role is unavailable.

06Memory metadata can disagree with session routing

Session start and search both agreed on dsh-mini-demo, correctly. A direct lookup on a single stored observation then came back with a header naming deepseek-harness instead, even though the content was plainly about the demo project. Two code paths inside the same memory system disagreed about which project they were looking at. Nothing leaked this time, but it is the kind of quiet inconsistency that matters more once memory holds something sensitive.

Implication: project-identity assertions belong in memory integrity checks, not just in session routing.

The goal is to earn stronger claims, not add more agents.

It would be easy to answer every finding above by adding a role: a cardinality enforcer, a lineage daemon, a project-identity oracle. I am deliberately not doing that yet. Five roles is already enough surface area, and every new agent is one more place where authority can leak, one more prompt that can be misread, one more thing that has to show up correctly in an audit trail. The roadmap below turns findings into tests and invariants first. A new role earns its place by surviving an experiment, not by sounding useful in a design meeting.

V0.2

Role conformance

Move mutability, reviewer immutability, worker limits, and authority boundaries from prompts into runtime policy, so "exactly one worker" is enforced, not merely requested.

V0.3

Multi-project memory isolation

Test several repositories, overlapping terms, renames, remotes, and monorepos, to find out whether the V0.1 near-miss was luck or a pattern.

V0.4

Failure recovery

Inject provider outages, quota exhaustion, timeouts, malformed child output, shell denial, and test failure, and check that each degrades loudly instead of quietly.

V0.5

Parallel isolated workers

Use Git worktrees and measure speedup, conflicts, duplicated work, integration errors, and token overhead against running the same work serially.

V0.6

Routing policy

Measure when a stronger worker or model-diverse challenger improves outcome enough to justify its cost, instead of assuming the strongest model always wins.

V0.7

Single strong agent vs hierarchy

Run the same 20+ task corpus under both conditions and compare correctness, time, tokens, retries, defects, and human intervention. This is the comparison the thesis stands or falls on.

V0.8

Long-horizon engineering

Test multi-hour work, context compaction, interruptions, resume, and intent drift, none of which a five-minute eval can exercise.

V0.9

Completion correctness

Turn "done" into a machine-checkable acceptance state with negative tests and incomplete-implementation traps, instead of trusting a child agent's sign-off.

V0.10

Adversarial security

Red-team repository prompt injection, memory poisoning, secret exfiltration, malicious MCP output, and destructive commands.

V1.0+

Autonomous security engineering

Apply the same role contracts to vulnerability validation, detection engineering, DFIR, and incident response, which is the actual reason I built this.

Metrics that should become first-class

That list is long because "did it work" collapses too many failures into one word. A run can pass its acceptance test and still leak a role violation, burn three times the tokens a single agent would need, or quietly skip the challenger. If I only got to keep three, I would keep task success, role violations, and token usage against a single-agent baseline: whether the output is right, whether the architecture I claim to run is the one that ran, and whether any of this is worth its complexity.

  • task success
  • acceptance criteria satisfied
  • tests passed
  • defects found after completion
  • unrelated file changes
  • delegation count
  • role violations
  • retry count
  • root interventions
  • human interventions
  • wall-clock time
  • token usage
  • provider cost
  • parallel speedup
  • merge conflicts
  • memory routing accuracy
  • memory retrieval precision
  • cross-project leakage
  • lineage completeness
  • rollback success
The experiment that matters most is simple: does hierarchical orchestration actually outperform one strong agent on a repeatable task corpus?

Until that A/B test exists, hierarchy is a plausible engineering architecture, not a performance claim.

What V0.1 proves, and what it does not.

V0.1 does not prove that hierarchy is cheaper, faster, or more correct than a single strong agent. It does not establish long-horizon reliability, adversarial robustness, or that any of this is safe to run unattended against production code. One passing run of one trivial task is not evidence of those things, and I would be skeptical of anyone who claimed otherwise from this little data.

What it does establish is a working control loop, once: planning separated from implementation, implementation independently verified, a model-diverse challenger reviewing the result, durable memory surviving across conversations, and failure modes observed precisely enough to become the next set of experiments instead of getting explained away.

What would change my mind is the experiment in section eight that does not exist yet: the same task corpus run once through a single strong agent and once through this hierarchy, scored on correctness, time, tokens, retries, and human interventions. If the hierarchy loses that comparison broadly, the extra roles are overhead dressed up as architecture, and I would say so.

Right now I have one clean run, six real findings, and a repository anyone can clone to check my claims instead of taking my word for them.
